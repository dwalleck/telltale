# 01: Can GitHub measure elapsed pull request time?

Type: research

## Answer

**Yes, for elapsed PR time, not reviewer effort or Jira time in status.** A read-only work-laptop spike started from Jira Development links for delivered non-Spike issues in the same exploratory sprint windows as the [first-commit study](../../first-commit-start/issues/01-can-jira-links-lead-to-a-first-commit.md). It used only the approved GitHub repositories and deduplicated PRs by repository and number. GitHub returned usable lifecycle dates for the sampled merged PRs. Not every delivered issue had an in-scope Jira PR link. The configured group limits were both off for this local check. The exact coverage and timings are in `notes/github-pr-timing-feasibility.md` in the local Telltale work folder, outside this checkout.

| Candidate | Source and evidence | Limit |
| --- | --- | --- |
| **PR open to merge** | `created_at` to `merged_at` from [Get a pull request](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request). Observed on the enterprise host. | Includes draft time and can include time spent closed before reopening. Open or closed-unmerged PRs need separate treatment. `closed_at` is not a substitute for `merged_at`. |
| **Ready for review to merge** | Use [timeline events](https://docs.github.com/en/rest/issues/timeline#list-timeline-events-for-an-issue), including [`ready_for_review` and `convert_to_draft`](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types#ready_for_review). Timeline reads worked. The linked sample used opening as the inferred ready time; a separate spot check confirmed an explicit timestamped ready transition. | Mark inferred starts as such. Repeated draft/ready transitions and close/reopen cycles need explicit rules. The spot check did not validate a return-to-draft case. |
| **Open or ready to first submitted review** | Paginate [List reviews for a pull request](https://docs.github.com/en/rest/pulls/reviews#list-reviews-for-a-pull-request) and use `submitted_at`. Observed on the enterprise host. | Pending reviews and ordinary comments are not submitted reviews. Actor type and Copilot flags can exclude some automation, not prove who did the work. This is elapsed time to a visible event, not reviewer wait across the whole PR. |
| **Time to first visible approval** | The same reviews list has `state` and `submitted_at`; `APPROVED` reviews were observed. The timeline documents [review dismissal](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types#review_dismissed). | First visible approval is not when all required approvals were satisfied. Historical rules, dismissal, new pushes, and reapproval can change that. |

The probe paired GitHub open-to-merge with Jira's recorded Code Review stays only for issues with one linked in-scope PR, no additional visible links or lookup errors, and a merge by delivery. The GitHub interval was longer in some pairs and shorter in others. That is expected: these metrics have different endpoints. Jira's comparison used elapsed hours in recorded status through delivery, not the sprint report's business-time calculation. No conclusion about the size or prevalence of differences in the wider team follows from the exploratory sample.

## Follow-up: coverage depends on where collection starts

The original probe counted **Jira-linked delivered issues**, not the PR population. A separate GitHub-first inventory paged the approved repositories and used GitHub merge timestamps to select PRs in the same closed sprint windows. It found more usable open-to-merge timings even in the focus repository alone. For PRs whose branch/title key resolved to a Jira issue absent from the local store, a follow-up verified that every missing issue was in a project outside the saved Jira import scope. The configured project list agreed with the saved import scope. That is expected with a GitHub repository that receives PRs for other Jira projects, not evidence of a failed import or of a missing Jira Development link. See `notes/github-pr-timing-missing-jira-issues.md` for the scope check and `notes/github-pr-timing-out-of-scope-projects.tsv` for the verified project keys, names, and counts. Both are in the local work folder, outside this checkout. Other Jira-first filters, including the recorded-review-stay requirement for the paired comparison, should not be applied to PR-native timing. Exact counts and reason breakdowns are in `notes/github-pr-timing-coverage-audit.md` in the local work folder. The inventory covers approved repositories only and does not establish that every PR belongs to this team. *(Observed.)*

## Recommendation for a spec

- Start with **PR open to merge**, per distinct merged PR, collected directly from GitHub and assigned to sprint windows by merge time. Use Jira linkage for the separate paired comparison, not as a prerequisite for PR-native timing. Define team and repository scope explicitly. Report unmatched issues, links outside scope, and read failures separately. The Jira Development endpoint is internal; keep the [branch/title alternatives](../../first-commit-start/issues/01-can-jira-links-lead-to-a-first-commit.md#4-is-the-date-believable) available to evaluate before settling on a production linkage route.
- Keep PR time as a secondary measure alongside **Jira time in Code Review**, not a correction or a substitute. Keep the draft and reopen semantics explicit, select elapsed or business time deliberately, and do not sum overlapping or stacked PRs into an issue total. Apply the configured group rules to the actual contributors.
- Add **ready to first submitted review** only after agreeing how to handle inferred readiness, draft and reopen histories, automated reviews, and missing events. Defer historical required-approval timing and reviewer-versus-author wait until they have their own evidence and definitions.
- The spike used read-only GETs through the signed-in GitHub CLI. GitHub documents **Pull requests: read** as sufficient for PR metadata, reviews, and timeline reads; an appropriately restricted credential still needs verification on the enterprise host for production use.

No production code, config, or primary metric changed.
